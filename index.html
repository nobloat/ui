nobloat/ui

Less, but working.

The motto plays on Dieter Rams’ Weniger, aber besser (“less, but better”), his book on what good design leaves out. Ours asks for one thing more: whatever stays has to work, every time, for everyone.

Software has become heavy. Frameworks, libraries, toolkits, build tools, node_modules, dependency hell. Software gets written faster than ever, partly thanks to AI, and every one of those dependencies is a supply chain risk.

It is bad for users too. Usability and accessibility often get buried under a “new” or “modern” design language.

And the dependency mess has a cost of its own. Software loads slowly and needs more hardware. Devices get replaced long before they wear out, just because “modern” software asks for more than they have.

nobloat tries another way. Back to the roots. Use what almost every system already has: a browser. Browsers have become really capable, with offline support, every platform covered, and much more built in.

The goal is a whole system with as few dependencies as possible, ideally none, that is pleasant to use, with great usability and accessibility.

None of this is new on its own. The combination is what makes it different.

Philosophy

nobloat is pragmatic software minimalism. Pragmatic, because the goal is software that works well, not the smallest possible number of anything. A dependency can be the right call. It just has to earn its place, like everything else.

Three ideas carry the rest.

  1. Respect the human

    Their time, attention and device are not ours to spend. nobloat software is efficient and functional, built for people who use it every day: dense where it helps, fast with the keyboard, no clicks wasted. And nobody is left out in the rain. Whoever arrives for the first time, on a phone or with a screen reader, finds their way too.

  2. Respect the planet

    Software should not be the reason a working laptop or phone ends up in a drawer. Small pages, little code and no needless requests mean less energy, less hardware and devices that stay useful for years.

  3. Re-use what is there, understand what you add

    The browser, the operating system, plain files and the standard library already solve most problems. Build on them, and keep what you add small enough that someone knows why every line is there. A little copying is better than a little dependency: a PDF writer is about 400 lines of the standard library, not a library with its own dependencies. What you understand you can fix, change and keep running. What you only import, you just hope about.

History

nobloat started during COVID-19, as a handful of small tools I wrote for myself, each a minimal alternative to a well known one: blog instead of Hugo, poll instead of Doodle, up instead of Uptime Kuma, split instead of Splitwise, workq instead of River, tinyviper instead of viper. The blog exists because every static site generator I tried broke its build after a year or two. The poll exists because a Doodle page loaded 4.7 MB of JavaScript to ask when people have time. Mine does the same with about 27 KB.

Each one was its own little answer to the same question: what do I really need, and nothing more? But they stood alone. Every tool solved its look, its login and its build again, a bit differently each time.

Then it sat frozen for a long time. Now I have found the joy in following the nobloat path again, and this time the ideas get a central place. nobloat/ui is that place for the look and behaviour, and the apps (bill, track, up, jot, call and the rest) share it, along with one login and one way of running them, instead of each starting from scratch.

The newer nobloat apps were all born out of frustration with existing software. Nothing quite fit for me. I don’t claim they fit anyone else, but they express my beliefs, visions and ideas of what software should look like. It ain’t perfect either, of course.

Principles

The three ideas, applied to the screen. What a human using a nobloat app can rely on.

  1. Nothing more than needed

    Every element has to earn its place. No feature, setting or animation just because it could exist. Every app names the tool it replaces and lists what it deliberately does not do.

  2. Fast on any device

    A page weighs kilobytes, not megabytes, and shows up at once. A ten year old laptop stays good enough.

  3. Keyboard first

    Every action has a shortcut. The mouse is welcome, but never required.

  4. Same everywhere

    The same thing looks the same and sits in the same place in every app. Learn one, know them all.

  5. Says what happens

    Every action has an icon and a word. One main action per page. Anything that destroys asks first and names what is lost.

  6. Nothing gets lost

    What you see is in the address, so reload, Back and a shared link open the same view. A failed save keeps what you typed.

  7. Your data stays yours

    Everything an app keeps is plain text in files: CSV, JSON and key = value. You can read it, back it up, move it and fix it with any editor, without the app and without a database.

  8. Accessible by default

    High contrast, a visible focus, big enough targets, and meaning never told by colour alone.

  9. Works everywhere

    Phone to desktop, light and dark, with JavaScript switched off. The page never scrolls sideways.

  10. Prints on any printer

    Invoices, letters and reports print fully readable on a cheap black-and-white printer, with as little ink as possible.

  11. Built to last

    Plain HTML, CSS and a little JavaScript, all understood and all in the repository, small enough to read in one sitting. Nothing to update every other week.

The system

nobloat is more than a look. Every app stands on the same few foundations, and each one is written down once: as a skill (the rules a person or an agent follows when building) or as a small component of its own. An app takes what it needs and adds only its own work.

Foundations

  1. Storage

    No database. Configuration is key = value with environment overrides, entities are small .conf files that reload while the app runs, data is JSON per object or CSV and JSONL rows. Every write is atomic, concurrent edits carry a revision, and a backup is a copy of the folder. nobloat-storage

  2. Outbox

    Whatever leaves the system (mail, webhooks, pushes to other services) is first a file in outbox/, written together with the change that caused it. A worker sends it, retries with backoff and finally moves it to outbox/failed/ for a human. The folder is the queue, so ls is the debugger. nobloat-outbox

  3. workq

    A small job queue for work an app does later, in the background, instead of a queue server. A component, not a skill. nobloat/workq

  4. Auth

    Two modes and nothing else: basic auth when one person uses an app alone, or nobloat/auth in front of every app, one account for all of them. nobloat-auth

  5. UI

    This design system: the rules, the parts, and the Go types that put them together. nobloat-ui, rules in design-system.md

How the UI is stitched together

Every part lives in a folder of its level (tokens, components, blocks, shell) with its CSS, its template and, only when it has behaviour, its script. Its Go type is its interface: the fields are what can be set, and rendering refuses what the rules forbid, such as a button without an icon, a second primary action or a field without a label. A page of an app is a Go value built from these types; ui renders it, and the app's test collects exactly the CSS and JavaScript its pages use into one ui.css and one ui.js. Behaviour with settings is a custom element in the light DOM, so the page works and reads without JavaScript first.

How the apps talk to each other

Calls go one way: the app that depends calls the other, never back. The caller is a service user in auth with a key and the groups that decide what it may reach, and it calls through the proxy, so auth checks the key like any other request. Changes that span two apps carry a stable reference and the revisions they read, so a retry is harmless and a stale read is refused; when the other app is down, the caller refuses instead of guessing. Mail and webhooks go out through the outbox. nobloat-system

How auth is managed

Groups are the only source of access. Users and roles are files in auth's data folder, and every app is one <id>.app.conf that names the groups allowed in. In front of nobloat apps, the proxy asks auth for every request and passes who and which groups in Remote-* headers; the app only reads them. Apps from elsewhere sign in with OIDC (Grafana, Forgejo) or SAML (BookStack). API keys and service users are issued by auth, never by the apps, so taking a group away takes the access away everywhere at once.

The skills

  • nobloat: the taste and the workflow for every project: Go and its standard library, plain files, plan first, then build in one pass.

  • nobloat-system: several services as one system: integrations, money and documents, own renderers instead of libraries, the security baseline, the local stack.

  • nobloat-storage, nobloat-outbox, nobloat-auth and nobloat-ui: the foundations above.

  • Components without a skill: workq (jobs), and in the local stack nomail, a mail sink that keeps every mail the apps send.
